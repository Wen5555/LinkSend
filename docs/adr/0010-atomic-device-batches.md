# ADR0010：持久化多设备分发批次

日期：2026-10-18。状态：设计，尚未实现；不作为N2完成证据。

同一Go持久草稿保存多个明确目标，批次命令提交精确草稿revision、request ID和等待离线设备的选择。Go核对全部目标当前已配对身份、授权代次、来源和规则，准备一次初始内容身份后，在单个SQLite事务内写入批次及全部独立子队列；任一预检/插入/提交失败都不能留下部分批次。不由JavaScript循环Enqueue。批次与子请求各自稳定、重复目标拒绝，同request不同来源/规则/目标/等待策略拒绝；完成请求在草稿清空后仍返回原收据。

首版继续原有进程级顺序派发，一个活动文件任务。每个目标保存授权代次、源摘要、规则和独立queue/task状态；每次派发重新核对源，源变化要求新确认，不声明冻结快照。一个目标离线、撤权、失败或取消不撤销其他目标已提交的文件。继续/重试复用该子任务，只重试用户选择的未完成者；主草稿后来修改不改变已有批次。

批次取消先持久化取消意图并停止尚未开始的子项，再通过现有任务控制取消唯一活动子项；已完成目标保持。取消与恢复/派发需使用同一Go owner门闩，重启后不自动派发旧批次，明确确认仍受原授权代次和源规则限制。批次状态由持久子项和取消意图汇总，不以按钮状态冒充全部完成。

计划任务库10→11，沿用可读备份/校验/事务迁移，增加草稿目标列表、批次与子项关系。文件wire、真实Pion/QUIC、身份pin、hash、安全落盘和relay=false保持；仅本地控制元数据扩展。具体列、上限和API以实施核对后补齐，不把本设计草案当实现。

## 下一实施切片

1. Go草稿持久目标列表，首版目标数有界（建议2–16），拒绝重复/未配对目标，保留单目标旧字段和完整发送默认。批次API从已保存草稿取路径、N1规则与目标列表，不接受JS提供正文或循环单目标入队。
2. 批次request先核对既有幂等收据；相同草稿引用/选项在草稿清空后仍返回原结果。新请求在哈希前和提交事务内重验草稿revision/规则/目标；全部子项同事务保存授权generation与内容身份，使用稳定派生子request ID。用SQLite trigger中断第三个子项取得真实回滚负例。
3. 复用当前顺序队列，不新增文件并发。批次摘要从全部持久子项汇总，普通队列分页和个体取消/重试保留；批次标识不作为新授权。
4. 取消意图需要覆盖“DB已提交、活动任务尚未来得及取消就退出”的窗口。启动恢复、ConfirmQueue、直接ResumeTask/RetryTask都不能绕过已取消批次。先以持久task完成回执识别真正成功者，剩余项取消，不把已安全提交的接收文件删除或伪称未完成。不得只在UI阻止恢复。
5. 三目标夹具证明在线/离线/撤权和源变化的独立子项行为；先成功目标不重复发送。Go和desktop两个模块及GOWORK=off、针对性race、真实绑定/前端/原生入口按实际结果补齐，再阶段推送。现有N1包source0499cb5不等于N2包。
