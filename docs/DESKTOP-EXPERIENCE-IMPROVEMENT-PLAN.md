# LinkSend 桌面体验与可靠性改进方案

日期：2026-09-13  
状态：供后续实施的详细方案；本次只做调研和文档，没有修改产品代码或发布软件。  
需求来源：张耀文对最新软件的七项测试反馈，以及引用讨论《完成桌面端六项功能》。

## 1. 基线、范围与交付定义

本地 HEAD 与本次 `git ls-remote origin refs/heads/main` 均为 `3bcb73019d1ac6de1d9f341bb7d22e2813875081`。当前测试预发布为 `v0.5.0-m5`，发行源码为 `d0c4a4b13ddc5bd7cd42c8f977d7aa6f7897ae06`；主分支后续提交补充发布记录。不要将本文的新方案当成已经实现的能力。

产品目标：**文件分享少操作，设备关系可管理，连接状态可信；日常跨设备文字和图片交接改用明确开启的自动剪贴板同步。**

用户七项要求全部进入必交付范围。可以分里程碑测试，但不能用旧 SendTo/Services 冒充系统共享，不能用隐藏按钮冒充设备删除，不能以手动“发送剪贴板”代替自动同步，也不能只修改页面而跳过发现与配对后端。

| 编号 | 必须交付的结果 | 完成判据 |
| --- | --- | --- |
| U1 接收确认 | 显示发送设备、文件摘要、以后是否免确认；正常情况一次点击接收 | 无需点击预览计划、逐条勾选或再次确认重名处理 |
| U2 设备与配对 | 能删除设备；配对码直接配对；LAN 添加须被连接端同意；不引入管理员或账号流程 | 删除后不因刷新重新配对；双方及服务器状态有明确表达 |
| U3 LAN 发现 | 修复多网卡、降级与网络变化问题，借鉴成熟项目扩展可靠发现 | 对准确安装包完成物理网络发现、配对和双向收发验证 |
| U4 内容与剪贴板 | 删除独立文字、链接、图片手动发送模块；后续里程碑交付自动剪贴板同步 | 主界面无旧编辑器；授权设备间复制后能自动在另一端粘贴 |
| U5 设置 | 收集分散选项，按用途分类，统一保存反馈；重名策略在此设置 | 常用接收设置容易找到，配置不互相覆盖 |
| U6 原生共享 | Win11 系统共享与 macOS Share Extension 打开设备小面板，选设备发送 | 无需展开主界面；冷启动、后台驻留与连续共享均有效 |
| U7 界面长度 | 固定导航、分区与局部列表滚动，正常操作留在首屏 | 小窗口和系统缩放下主要操作可见，无页面随历史无限增长 |

沿用 Go 双模块、Wails 3、Pion ICE、quic-go、固定公钥、持久队列和已有安全提交/恢复机制。文件与剪贴板正文只走经过身份验证的 QUIC；服务器负责发现、配对和协商，`relay=false`。

此次反馈调整了旧规划：手动文字/链接/图片发送不再继续作为独立产品功能；自动剪贴板同步由此前不在范围内改为后续必交付里程碑。实施前应同步修改 SPEC、PRODUCT-PLAN、PROTOCOL、SECURITY 和相关 ADR，保留旧验收记录作为历史事实。

## 3. U1：一次确认完成接收

### 3.1 正常界面

```text
MacBook Pro 想向你发送文件
macOS · 已配对

课程报告.pdf
实验截图.png
以及另外 6 项                     共 28.4 MB

保存到：下载 / LinkSend          查看详情

□ 以后自动接收此设备发来的文件

                   [拒绝]  [接收文件]
```

- 展示本地设备别名、设备类型及简明关系状态；长指纹放在设备详情。
- 文件只显示前几个名称、总数和大小；完整清单按需展开，避免长列表撑高弹窗。
- 默认接收全部文件和空目录。普通流程不出现“拟接收条目”“预览保存计划”、全选/全跳过等实现术语。
- “查看详情”以只读信息为先；保留已有的按需选收能力在次级操作中，不作为每次接收的前置步骤。
- 每设备免确认只影响文件接收，不自动授权剪贴板同步；可以随时从设备详情撤销。

### 3.2 重名和异常处理

全局默认采用**保留两份，自动生成新名称**；设置提供“保留两份 / 跳过同名项 / 每次遇到冲突询问”。普通新用户不需要配置这一项。此轮不顺带增加现有后端不支持的静默覆盖。

策略优先级为：已存在的恢复计划 > 本次主动高级选择 > 设备专属策略 > 全局默认策略。前两者用于已授权任务；更改默认值不重新命名正在传输或恢复中的文件。

同名目录、大小写冲突、并发创建目标文件以及恢复重试都要使用同一套安全命名和提交规则。跳过项要写进实际结果；全部跳过应显示“未接收文件”，不能显示已经传输成功。

空间不足、目录不可写、源内容变化、身份异常等会影响结果的问题才进入“需要处理”。若旧端不支持选收/跳过，应说明兼容限制并让用户选择可执行方式，不能静默扩大接收范围。

### 3.3 后端实现

新增应用层普通接收命令，例如 `AcceptIncomingDefault(taskID, attemptID, revision, remember)`，具体命名在实施时确定。由 Go 读取生效策略、生成计划、检查空间与目录、核对任务代际并持久化同意；成功后才发送 accepted。前端不再人工串联生成计划和确认两次操作。

预检可以提前在后台执行，但不能提前发送文件正文；按下接收时仍核对计划、目录状态与撤销状态。重复点击、迟到事件和重复请求只能生成一次接收决定。免确认接收也走相同的计划与校验逻辑。

若本次同意已成功但免确认偏好保存失败，明确反馈“本次已接收，免确认设置未保存”，不要诱导用户重发。已有提交意图、文件身份和 SQLite 恢复记录继续保留。

**验收：**默认策略下，包括存在同名文件时，用户一次点击就能启动接收；重启恢复不生成第二份意外副本；修改设置不改变活动计划；取消和删除设备能阻止迟到 accepted 生效。

## 4. U2：设备可删除，配对流程完整

### 4.1 设备页结构

默认显示“我的设备 / 已配对设备”，附近未配对设备放进“添加设备”的独立区域。每行保留名称、系统图标、关系状态、连接状态和更多菜单。编辑别名、专属接收目录、文件免确认、剪贴板权限进入设备详情；不在每行展开大表单。

“添加设备”包含两种入口：输入配对码、查找附近设备。手工 IP 位于“没有找到设备？”的次级入口。

### 4.2 删除的明确语义

建议“删除设备”表示**从当前设备组移除该设备，并撤销本机对它的授权**；删除确认框用一句话说明会影响当前设备组，保留历史记录和已经收到的文件。仅移除收藏或“我的设备”标签是单独的展示偏好，不冒充删除。

任何当前有效成员均可在组内添加/删除设备，不要求管理员身份、账号登录或手工比对指纹。后台仍验证设备签名、组范围和授权；“没有管理员流程”不等于匿名调用删除接口。

删除顺序：

1. 本机先持久化撤销标记和授权代际，关闭免确认与剪贴板权限，清除常用排序和自动重试资格。
2. 停止该设备的活动连接与未完成发送；保留可恢复记录及用户文件，恢复必须重新取得有效授权。
3. 在线时提交幂等的组成员移除；通知其他在线成员同步撤销及状态。
4. 服务不可用时，本机立即生效，显示“已从本机移除，设备组变更待同步”；服务器成功前不声称全组完成。离线成员要在恢复连接并同步后才得知撤销。
5. LAN 公告、服务器旧快照、缓存和重启不能自动恢复旧信任。再次加入必须发生一次新的有效配对；文件免确认和剪贴板权限重新选择。

删除后不继续占据默认“我的设备”列表。持久撤销记录可放在设置的设备管理区域；附近重新发现同一身份也不能使它重新成为已配对设备。退出本机所在设备组使用明确的“退出设备组”，不通过删除自身实现。

需要调整服务端当前 `Admin` 检查以及本地仅靠 pin 的合并逻辑，并引入成员变更版本或等效撤销机制。组内变更不能越权操作其他组，旧邀请和旧授权不能复活已删除设备。

### 4.3 配对码

- 在另一端输入有效配对码即完成配对，不再附加被邀请端管理员批准、人工指纹或账号验证。
- 首台设备应能完成正常初始化并生成自己的配对码；技术上的服务部署初始化不进入普通桌面配对流程。必要时为首台设备提供受限、幂等的独立设备组初始化。
- 保留短期、单次、有限重试和同身份幂等消费。码错误、过期、已被其他设备使用、服务不可达分别提示。
- 同组已配对时直接显示“已经配对”，不创建重复设备，也不因重复配对提升接收权限。
- 若本机已属于另一个组，不静默合并两组所有设备：提示本机切换的后果，并在一致的成员变更事务中处理；保留身份和文件记录。
- 配对成功与对端上线分别表达：“配对成功，对方尚未上线”是合法结果。

### 4.4 局域网添加

流程：A 查找到 B → A 点击“添加” → B 显示 A 的设备名称和系统 → B 点击“添加设备”或“拒绝” → 双方关系落盘并显示已配对。

首次 LAN 添加确认属于建立关系；之后不在每次收件时重新询问是否加入组。拒绝或超时不能留下组成员、pin 或自动接收权限。重复请求只显示一次，拒绝后有冷却，双向同时添加要幂等合并。

控制请求绑定双方公钥、请求 ID、失效时间和随机 nonce，通过验证身份的临时 LAN TLS 通道完成；发现公告本身不授予任何权限。对同名但密钥不同的设备，不静默继承旧关系。

加入服务器设备组时，由同意方授权服务端签发绑定已确认接收身份的短期加入凭证；凭证只经该 LAN 控制通道交给目标。服务不可用时可以完成本地配对，并显示“局域网已配对，跨网络配对待服务恢复”。本地配对成功不能伪称服务器入组成功。

### 4.5 可解释状态

关系状态和连接状态分别维护，界面合成一句清楚的话；不再仅靠一个绿色圆点。

| 已确认的事实 | 用户看到的状态 / 下一步 |
| --- | --- |
| 签名公告已发现，尚未配对 | 附近设备 · 可以请求添加 |
| 请求已送达或正在等待 | 等待对方确认 · 可取消 |
| 已配对，LAN 控制连接验证成功 | 已配对 · 局域网可连接 |
| 服务器连接与在线列表同步完成，对方未出现 | 服务器连接正常，尚未找到另一台设备 · 请在对方打开 LinkSend |
| 对方存在服务器在线记录，尚未直连 | 已配对 · 对方在线，连接时检查直连路径 |
| LAN 公告可见，但控制连接失败 | 已发现设备，暂时无法连接 · 查看连接检查 |
| 信令断开，但 LAN 或已建立数据连接可用 | 服务器连接中断，局域网/当前传输仍可用 |
| 身份固定值不匹配 | 设备身份发生变化 · 停止连接并处理配对 |
| 本机撤销已落盘、服务端尚未同步 | 已从本机移除 · 设备组变更待同步 |

“服务器正常”至少区分健康接口可达、已认证连接、在线列表已同步。缺少证据时显示“尚未检查/检查中”，不能把未知状态推断为离线或防火墙拦截。

**验收：**普通成员能删除并重新添加；删除后刷新、重启、WSS 重连和 LAN 再公告均不会复活旧授权；跨组删除被拒绝；配对码和 LAN 的同意要求各自成立；旧客户端同步不能绕过撤销。

## 5. U3：增强 LAN 发现和网络变化恢复

### 5.1 借鉴 LocalSend 的哪些部分

本次核实的 LocalSend 官方协议 v2.2 使用 UDP multicast 和 HTTP 双向登记；当前主分支实现增加了按接口/地址建 socket、IPv6、多地址记录和独立失败处理。主分支实现不等于某个已发布安装包的行为。

LinkSend 借鉴其**多接口处理、双向确认、多地址合并、分通道降级和可见的失败状态**，继续使用自己的签名发现、TLS 控制、Pion ICE 与 QUIC。不要替换成 LocalSend 的 HTTP 文件上传协议，不宣称两软件可以互传。

LocalSend 的网段扫描兜底不直接采用：当前项目约束是不扫网段，使用记忆地址、用户明确输入的 IP 和服务器路径。mDNS/DNS-SD 可评估为新增补充发现通道，但本次核实的 LocalSend 机制不能称作 mDNS；mDNS 同样不能绕过网络隔离。

### 5.2 第一批必须修复的源码缺口

1. `refreshInterfaces` 当前每接口只保留首个 IPv4：改为枚举接口上的有效地址及前缀，避免遗漏另一可达网段。
2. multicast 接口不可用或全部加入失败时，当前 discovery Manager 整体启动失败：拆分组播、广播、受限单播和 TLS 控制生命周期，局部失败不关闭可用通道。
3. 单播/广播复用 wildcard UDP 且未明确指定源接口：按接口地址约束发送、记录收包接口和回程，尤其验证 Windows 多网卡与重叠私网。
4. 同网卡 index 下地址变化、socket 持续报错和接口刷新失败：增加可观测状态、退组/重入、退避重建和错误上限，避免无效循环。
5. 记忆地址不能只在启动时探测一次：保留有界地址历史，按当前 on-link 条件验证并退避探测，地址重用必须核对公钥。
6. 补齐 peer、route、响应限流表、握手 goroutine 的总容量和过期清理，避免附近大量公告造成无限资源增长。

### 5.3 统一设备目录和发现通道

按长期 DeviceID 合并服务器在线状态、LAN 公告、主动确认和记忆地址，同一设备多块网卡只显示一行。每条地址记录来源、接口、本地源地址、地址族、网络代际、最后出现时间和实际验证结果。

启动、打开添加设备、手工刷新以及网络变化时，发起带抖动的短时多轮发现；后台逐步降低频率。旧设备变成离线状态而不是不断闪现/消失，过期地址不能当作当前可达路径。

保留独立的：IPv4 组播、每接口广播、受限单播、记忆地址与 WSS。双栈和 mDNS provider 在上述主路径修复后进行原型验证；IPv6 发现、TLS 控制和 QUIC 文件传输要分别通过，不能仅凭设备出现就宣布 IPv6 可用。若 LinkSend 和 LocalSend 同机运行，验证各自端口、协议校验和资源互不干扰。

### 5.4 网络变化

接入 Windows/macOS 网络及睡眠唤醒事件，并保留低频快照比对；覆盖 Wi-Fi、DHCP、VPN/TUN、默认路由和网卡状态变化。消抖后只重建受影响的发现 socket、候选和连接缓存。

健康的 QUIC 传输不因一次发现刷新或 WSS 断连被取消。路径确实失效时，废弃旧 generation，用新协商和已有恢复检查点继续。先完成可靠重连恢复，不承诺透明 QUIC 迁移。

### 5.5 可测量的验收目标

拟议目标：在允许设备互访的家庭网络中，冷发现 p95 不超过 3 秒；网络稳定后恢复发现不超过 5 秒。这是待基线测量后冻结的验收目标，**不是当前测得的结果或校园网保证**。

物理矩阵必须包含：Wi-Fi↔Wi-Fi、Ethernet↔Wi-Fi、校园混合网络、热点、多网卡、VPN/TUN 开关、DHCP 变化、睡眠唤醒和软件启动顺序交换。每项分别记录发现、控制可达、配对、Windows→Mac 和 Mac→Windows 文件哈希。

故障矩阵包含：组播失败但单播可用、公告可达但控制连接失败、服务器断开、端口占用、重复公告、多地址同一设备、无可用直连路径。IPv6 与真实跨 NAT 单列验收。网络不允许直连时给出有证据的失败阶段，不能靠延长超时或改主机防火墙把失败掩盖。

## 6. U4：移除手动内容发送，交付自动剪贴板同步

### 6.1 立即清理产品入口

从传输页移除“文字、链接与图片”编辑器及对应创建/发送入口。历史已接收内容仍可查看，已有草稿和暂停任务必须明确处理，不删除用户收到的文件。

旧手动内容队列升级后进入可见的“旧版内容任务”处理区，不悄悄继续自动发送；可恢复任务保留其快照并让用户决定完成或取消。旧协议的解析、历史读取及兼容接收可以保留过渡期，但新界面不继续提供手动内容创作功能。相关清理工具移到存储设置，旧数据不能突然失去管理入口。

### 6.2 用户体验与授权

设置中增加“剪贴板同步”：总开关默认关闭；选择允许的已配对设备，分别设置发送、接收方向与内容类型。第一次开启时清楚说明会自动读取本机剪贴板并可能写入另一端；双方各自允许相应方向后正常复制不再逐次确认。

先交付纯文本（链接按文本处理）和可开关的截图/图片。文件引用仍走文件分享，HTML、富文本、任意自定义格式不在首版自动同步范围。

托盘/菜单栏提供暂停同步和恢复同步；设备删除或身份变化立即撤销权限。文件免确认、配对关系和剪贴板权限三个状态独立，升级不能自动把原文件免确认变成剪贴板授权。

### 6.3 必须设计的行为

- **防循环：**事件包含来源设备、来源代际、序号、类型和内容摘要；写入远端内容产生的本机通知不能当成新的本地复制再广播。
- **并发复制：**定义可重复的事件排序与冲突规则，不依赖两台机器墙上时钟完全一致。接收/解码期间若本机产生新复制，旧远端内容不迟到覆盖；多设备不得互相循环覆盖。
- **不回灌旧内容：**离线时不积攒剪贴板历史；重连默认等待新的复制事件，不自动把断线前的旧内容覆盖到另一台设备。过期的未提交事件直接丢弃。
- **快速复制合并：**读取前后核对系统剪贴板代际；连续更新只保留仍有效的最新待发事件。正文大小、图片尺寸、解码内存和发送速率都有上限。
- **系统边界：**锁屏时默认暂停自动读取/写入，恢复后不补发锁屏期间内容；可识别的禁止同步/敏感标记尽力尊重，不宣传能识别所有密码。
- **记录最少信息：**默认不保存剪贴板历史，不将正文写日志；临时图片快照在结束或过期后回收，失败状态显示同步设备和原因即可。

### 6.4 技术路线与依赖

Windows 使用官方 `AddClipboardFormatListener` / `WM_CLIPBOARDUPDATE`；macOS 基于 `NSPasteboard.changeCount` 进行可暂停、有节制的检测，沿用原生格式读取与写入。采集、快照和网络传输在原生/Go 后台进行，JS 只接收状态和受限元数据。

新增明确的剪贴板能力协商；旧端显示“此版本不支持剪贴板同步”，不能静默转成文本文件不断接收。

现有全局单活动任务队列不足以承载持续同步。先完成同设备认证会话复用和有界文件/剪贴板处理：剪贴板不能一直排在大文件之后，也不能饿死文件传输。取消文件任务只取消它的流，暂停同步只停止剪贴板事件；网络失效、退出和撤销负责关闭相应会话。

这不是简单增加一个监听开关。自动同步作为本轮后续必交付阶段，必须连同权限、防循环、时效、大小限制和资源调度一起验收。

**验收：**Windows↔Mac 文本、链接、图片自动复制/粘贴；连续复制、两端同时复制、多设备回环、锁屏、离线重连、权限撤销、旧端不支持和大文件传输期间同步。测试使用隔离用户或可丢弃环境，不读取日常剪贴板做无关采样。

## 7. U5：统一设置与诊断

主导航名称改为“设置”，使用左侧分类、右侧单页内容；诊断成为独立子页。只渲染当前分类，而不是把全部设置换成一长列折叠卡片。

| 分类 | 主要设置 |
| --- | --- |
| 通用 | 本机名称、外观、语言（仅展示已支持项）、快捷面板快捷键 |
| 文件接收 | 默认目录、同名策略、按设备覆盖入口、文件接收通知 |
| 剪贴板同步 | 总开关、设备、方向、文本/图片、锁屏与暂停状态 |
| 系统集成 | Windows 共享目标 / Mac 分享扩展状态、原生入口启用帮助、兼容 SendTo/Services、登录启动、关闭窗口行为 |
| 网络与发现 | 附近可发现开关、服务地址；高级区域包含接口优先级/排除、绑定地址、STUN |
| 存储与记录 | 历史保留、旧内容快照、可恢复暂存占用；分别清理记录和应用暂存 |
| 诊断与关于 | 本机接收、发现通道、已认证服务连接、对端连通性检查、脱敏导出、版本与构建来源 |

传输页只显示一行接收就绪状态和当前保存目录，点击目录跳转设置；设备详情只保存该设备的覆盖值。覆盖界面应显示“继承全局”，避免用户忘记实际生效规则。

统一保存规则：开关在后端持久化成功后显示“已保存”，失败则恢复原状态并保留错误；文本/地址编辑在提交该字段时校验保存。安装、卸载入口和清理属于显式动作，单独执行。取消全页混用的“保存设置”概念。

实现上使用带 revision 的局部更新，避免后台选项和网络表单各自提交整份旧配置相互覆盖。需要重建网络或下次任务生效的设置，在对应字段旁说明；保存设置不能中断健康传输。

诊断默认给出下一步建议：设备未找到、LAN 控制不通、正在等待接收、直连路径未建立、任务可恢复等。ICE candidate、接口索引、TLS 参数、时序和稳定错误码放在详细证据里，导出默认脱敏。

**验收：**两次导航内找到同名策略；设置分类无超长整页；跨窗口/后台并发更新不丢字段；当前值、生效值、待生效原因一致；清理记录不删除收到的文件。

## 8. U6：原生系统共享与设备小面板

### 8.1 统一体验

目标操作链：**选择文件 → 右键“共享” → LinkSend → 小面板选择设备 → 发送。**

```text
发送 3 个文件 · 42 MB                         ×

  MacBook Pro              在线 · 局域网
  Windows 笔记本           在线 · 跨网络

  其他设备 / 添加设备
```

文件已由系统选好，点击已配对目标直接提交发送，不再增加“保存草稿”“加入队列”的人工步骤。离线设备放次级区域，选择后明确询问是否本地等待；附近未配对设备进入添加流程。用户可展开文件摘要，取消面板不发送。

正常只激活小面板。选设备后，后端持久化成功才反馈“已加入发送”；真正完成由状态或通知告知。主窗口保持原来的打开/隐藏状态，不因共享而强制切到传输页。

小面板具有自己的有界共享请求，不能自动混入主界面尚未发送的草稿。连续共享、同实例转交、扩展重试和双击设备均用请求 ID 去重。

### 8.2 Windows 11

采用正式 **Share Target** 激活入口，接收系统 `ShareOperation` / `StorageItems`。保留 Wails/Go 主程序，增加 C++/WinRT 或轻量 .NET 原生适配器；最终语言由原型和打包成本确定。官方桌面示例已证明无需整体迁到 UWP，但必须实际处理 WinRT 激活和异步文件获取。

优先原型：保留现有 NSIS，增加经过签名的 identity package（package with external location）。安装器负责身份注册、升级及卸载；若验证后发现组合维护成本更高，再评估整体 MSIX。不能只修改 Wails manifest 就认为系统共享已经接通。

普通便携 ZIP 没有安装身份，不默认承诺系统共享。它可以运行主程序和其他已有入口，但完整系统共享验收以安装版为准。发布包的签名信任是交付依赖，需要实际验证，不把开发机自签配置算作普通用户安装成功。

`IExplorerCommand` 可增加 Win11 第一层“使用 LinkSend 发送”快捷项，也可处理系统 Share 对目录支持不足的情况；这是额外快捷入口，不能替代本项要求的系统共享。

### 8.3 macOS

新增真正的 **Share Extension（.appex）**，在 Finder“共享”中显示 LinkSend。扩展提供原生自定义设备选择面板，界面由系统承载；已有 Services 留作兼容路径。无需将 Wails WebView 强行塞入扩展。

扩展通过 App Group 与经验证的本地交接机制向 Go 后台提交请求；Go 仍是身份、任务库和队列的唯一所有者。后台未运行时的唤起方式必须使用目标系统支持的路径实测，不能假设 Share Extension 随时可以调用主程序。

扩展生命周期很短，不能承担长期 QUIC 传输。文件引用需要转成后台真实持有的访问权：临时文件表示在有效回调内持久接管；需要跨进程或重启访问时，按系统语义交接 bookmark/授权并验证后台可读，不能只传字符串路径。

Apple 文档明确 `loadFileRepresentation` 的临时副本会在 completion handler 返回后删除。这是冷启动、共享源退出与恢复验收的重点。只有系统提供临时表示时才做必要复制，不能为了接入共享默认复制整份超大本地文件。

规范的签名、扩展 entitlements、App Group 和公证属于安装包前置条件。现有 ad-hoc 未公证 DMG 无法代表最终扩展行为。

### 8.4 两个平台都要处理的文件边界

真实路径、临时副本、虚拟文件、云端占位文件、共享源退出、文件变化和权限失效分开处理。尚需下载/准备的文件显示“准备文件”，不能提前显示已发送。不能把系统 API 给出的临时路径当作长期可恢复来源。

文件字节不走 JS、信令或共享扩展的自建上传服务。Windows 本地 IPC 限定当前用户，macOS 交接限定允许的 App Group/进程身份；路径当数据处理，不拼成 shell 命令。

可以承诺“分享后只出现设备小面板”。精确位置、系统弹层样式和关闭行为受操作系统控制；不承诺与鼠标固定距离，也不把 LinkSend 设备插进 AirDrop 或 Windows Nearby sharing 的系统设备列表。

**验收：**准确安装包在系统共享中出现；冷启动/后台/主窗已打开三种状态只激活小面板；文件、多文件、中文长路径、大文件、云文件逐项通过；关闭扩展后任务继续；取消不发送；重复共享不重复提交；安装、升级、卸载与签名信任可复现。文件夹支持按 OS 版本单列，不把兼容入口冒充系统原生支持。

## 9. U7：缩短页面，保持操作可见

保持四个主入口：**传输、记录、设备、设置**。“记录”承接现有收件箱和已结束任务的查询、定位与恢复操作。

- 传输页默认只显示文件选择、目标设备和“发送”主按钮；“进行中”“待发送”用页内切换展示，不在文件编辑器后无界堆叠。
- 接收就绪状态收成顶栏的一行信息；完整接收配置转到设置。
- 文件/任务/设备列表采用限高与虚拟化或分页；总数与主要操作始终可见。大批量条目不逐个创建所有 DOM。
- 设备详情改为侧栏/独立详情，不让每个设备的编辑表单把整页撑长。
- 固定主导航和必要工具栏，每个视图只有一个主要滚动区；大清单需要内部滚动时避免多层滚轮争抢。
- 接收弹窗和快捷面板均有最大高度、固定底部操作、键盘导航和焦点恢复。Esc 关闭预览不应取消后台正在发送的任务。
- 缩短解释性段落，将低频说明放进帮助或详情。不要通过缩小字体、压缩点击区域来减少高度。

拟议视觉验收基准：主窗 1100×720 逻辑像素下，正常选文件、选设备和发送无需整页向下滚动；960×640 与 Windows 125%/150% 缩放仍可操作，无水平滚动、被遮住的按钮。小面板建议约 420×460，实际随平台排版和内容自适应，清单只在内部滚动。

这些是待设计稿和原生窗口验证的目标尺寸，不是当前软件已通过的结果。同时覆盖深色模式、中文长名称、空状态、后端错误、键盘操作与 reduced motion。

## 10. 引用讨论中应纳入的内核与后续功能

### 10.1 本轮必须纳入的支撑工作

**准确发行包的可靠性。** M5 记录中的物理正向内容协议成功，没有证明完整 ICE/原生 GUI 链路；反向曾出现 `no route to host`。从实际源地址/路由、socket 绑定、监听、隔离和抓包证据排查，保留每项 PASS/FAIL/NOT RUN 的真实边界。

**统一存储所有权。** 一个 profile 的任务、队列、接收计划、收件箱和事件提交使用明确生命周期的存储组件。普通进度允许受控合并；授权、入队、恢复检查点和完成承诺必须等待必要持久化。保留现有数据库 revision 屏障、文件提交意图和恢复语义，不能把跨文件系统一致性简化成一个 SQLite 事务。

**同设备会话复用与有界调度。** 现有 `PeerSession` 不等于已经实现多任务 QUIC 复用。先支持同设备连续发送，明确任务流、取消、空闲回收、身份撤销和旧端回退，再补文件与剪贴板共存的资源预算。不先开放任意数量的全局并发。

**真实性能基线。** 测冷启动/连续小文件、发现 p50/p95、大文件与海量小文件、数据库提交耗时、空闲 CPU/唤醒与内存。吞吐提升不得通过削弱 hash、落盘和恢复保证获得。

### 10.2 七项完成后的功能顺序

| 建议顺序 | 引用讨论的功能 | 本方案的处理 |
| --- | --- | --- |
| 已纳入 | 快捷发送面板 | 与系统共享统一；可从托盘/快捷键唤出文件发送面板，不重新引入旧内容编辑器 |
| 下一优先级 | 工程目录预设 | 完整目录默认；源码/发布产物排除规则可预览并撤销，不静默忽略 |
| 下一优先级 | 多设备分发 | 同一份已确认内容建立独立目标任务，可先顺序执行；目标间失败/重试独立 |
| 单独授权版本 | 一次性临时分享 | 单任务、单接收者、可恢复授权；不加入永久设备组，不复用本次长期配对语义 |
| 之后 | 常驻 CLI、手工执行的保存规则、限速 | 复用单 profile 后台和有界任务调度，逐项立项 |
| 暂不进入本轮 | 混合文字/链接交接包 | 与本次移除独立内容发送的方向不一致，不借后续功能重新塞回主界面 |
| 中期单独设计 | 授权目录取文件、定时/目录监听、应用更新 | 分别涉及读取权限、后台发送或发行信任，避免同时扩大本轮范围 |

自动剪贴板同步已被用户此次明确提出，不沿用旧讨论中“暂不做”的建议。上述可选功能不能挤占 U1–U7 的完成。

## 11. 交付顺序与依赖

以下是建议的实施里程碑，版本名可用 `0.6.0` 的分阶段测试候选；最终版本按实际兼容性和完成范围确定，不按日期强行发布。

| 阶段 | 交付内容 | 退出门槛 |
| --- | --- | --- |
| E0 基线与关键原型 | 固定 M5 包复现主要问题；网络发现/双向收发基线；Win11 Share Target 与 Mac appex 的包级最小原型；设计配对/删除/同步 ADR | 关键原生路径确实可执行，网络失败有证据；平台签名/授权依赖清楚，不能只停在前端 mock |
