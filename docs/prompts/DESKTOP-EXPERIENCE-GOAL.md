## 一、模型、角色与 Goal

1. 总控模型为 GPT-6，工具模型标识 `gpt-6-astra`，推理强度使用极高 `xhigh`。当前总控任务应由用户在客户端预先选择这个配置。不要把文字声明当作实际切换成功；如当前客户端配置可核实且不匹配，应明确说明如何切换，并先推进不依赖切换的材料读取。
2. 执行任务固定使用 `gpt-6-astra`、`thinking: medium`。创建任务和派发后续实现工作时显式使用这个配置；若调用不支持或被拒绝，如实报告，不静默换模型或强度。
3. 通过 `get_goal` 检查现有目标。没有当前目标时创建本轮目标；已有相同未完成目标时继续复用。目标应覆盖七项改进、平台/网络验收和阶段性 GitHub 同步。我没有指定 token budget，不自行设置预算，不以自行设定的额度提前结束。
4. 同时只有一个总控和一个主要执行任务。独立执行任务使用 `create_thread` 创建，不用当前任务内的短生命周期子 agent 替代；不要默认继续派生更多任务。
5. 总控负责需求覆盖、技术决策、任务拆分、证据审阅、必要的独立复核和下一批分配。执行任务负责产品代码、相关测试、工程文档、构建、授权范围内的部署和 Git 操作。总控不要与执行任务同时修改同一份代码、运行同一生产变更或操作同一 Git 工作区。
6. 不要停在规划、TODO 或“可以实现”。除必须由我提供的凭据、系统人工授权或真实不可绕过的外部条件外，持续自主推进到完成。正常实现选择、故障排查、测试修复、阶段推送和已授权部署无需重复向我确认。

## 三、本轮必须完成的七项结果

U1. 简化接收确认。正常只展示对端设备、文件摘要、保存位置、以后是否免确认和接收/拒绝；点击一次接收即可。后台自动生成、检查和持久化计划。同名默认保留两份，策略移到设置，详细清单和选收只在用户主动展开时出现。恢复沿用原计划，身份、完整性和安全落盘不得弱化。

U2. 设备可删除，配对完整。删除须撤销相应授权并防止服务器同步/LAN 公告自动复活；保留收到的文件与历史。配对码有效即直接配对；局域网添加必须被连接端确认。桌面不引入账号、管理员或人工指纹流程；后台继续验证设备身份和操作范围。显示已配对、等待确认、已配对但离线、服务器正常但另一端未找到、已发现但连接失败等真实状态。

U3. 增强局域网发现。借鉴已核实的 LocalSend 官方协议与当前实现，修复多网卡、多地址、组播失败拖垮其他通道、回程接口不明确、记忆地址、socket 错误和网络变化恢复。统一设备目录，区分看见公告与实际可连接；根据验证结果增加合适的新发现能力，不擅自改成其他文件传输协议。

U4. 移除独立文字/链接/图片手动发送界面，并完成自动剪贴板同步。妥善迁移旧内容任务与记录；自动同步按设备、方向、类型明确开启，包含文本/链接和图片，具备暂停、锁屏处理、权限撤销、防回环、过期丢弃、大小/资源限制。不要把这项无限期挪到以后，不以手动发送剪贴板代替。

U5. 整理设置与诊断。按通用、文件接收、剪贴板、系统集成、网络、存储、诊断等用途分类；同名策略集中设置，设备专属设置可继承全局。统一保存反馈，局部配置更新不能互相覆盖，保存设置不能中断健康任务。

U6. Win11 与 macOS 原生共享加设备小面板。文件管理器右键系统共享→LinkSend→只显示可用设备的小面板→点击已配对设备提交发送；不强制展开主界面。Windows 使用真正 Share Target，macOS 使用真正 Share Extension，现有 SendTo/Services 只作兼容入口。原型及正式包分别验证身份/签名、文件授权、冷启动、后台交接、扩展退出后继续传输、安装升级卸载。不能用假设备列表或浏览器 mock 冒充完成。

U7. 缩短页面。正常选文件、选目标、发送在常用窗口首屏可操作；导航和主要操作稳定可见；任务、历史、设备和设置分视图，长列表有界渲染。验证小窗口、中文长名称、系统缩放、深色模式和键盘可访问性，避免靠缩小字体和按钮解决高度。

支撑工作同时纳入：持久化所有权、必要的会话复用和有界调度、真实跨平台双向收发及恢复、准确发行候选包验收。工程目录预设、多设备分发、一次性临时分享等附加方向排在七项达标之后，不抢占本轮。

2. 需要新建时先 `list_projects`，确认项目路径和 `isGitRepository`；在该项目新建一个独立 worktree 的执行任务，模型 `gpt-6-astra`，推理 `medium`。明确从当前工作区状态创建，包含本轮必要的未提交方案文件；确认新 worktree 中方案可读。
3. 使用一个 `codex/` 前缀工作分支，例如 `codex/desktop-experience-upgrade`；已有合适分支时复用。避免两个任务各自修改一条相同名称的分支或重复合并。
4. 创建若返回 `clientThreadId`，等 setup 完成取得真实 `threadId` 后，再调用需要真实任务 ID 的工具。记录 `threadId`、`hostId`、worktree、branch、模型/强度和阶段，不伪造创建成功。
5. 执行任务是产品工作区的唯一写入方，负责同步代码与工程记录。总控审查对应提交和证据；需要独立构建/复测时使用不会干扰执行工作区或用户 profile 的环境。
6. 总控把七项要求、授权边界和当前 TODO 明确发给执行任务。不要只发“继续干”而让它猜目标，也不要一次让它自行决定并跳过所有后续验收。

按完整方案 E0–E5 起步：

- E0：准确包基线、问题复现、LAN/双向网络验证、Windows Share Target 和 Mac Share Extension 包级最小原型、配对/撤销/同步 ADR。
- E1：设备删除和配对状态、LAN 发现与网络变化恢复。
- E2：一次接收、设置整理、页面结构和移除旧内容入口。

每次分派包含：本批 TODO ID、具体问题与结果、可修改范围、依赖、必要测试、允许操作的主机、回报格式。执行任务应完成整批并修复本批失败，提交验收证据后等待总控评审，不自行删除后续要求。

## 七、自动监督闭环

使用 `send_message_to_thread` 分派；使用 `wait_threads` 等待实际完成或需要处理的事件；需要具体上下文时再 `read_thread`。创建执行任务后必须开始等待实际进展，不能只创建就结束总控目标。

每轮闭环：

1. 查看执行状态、最新 TODO、提交和证据位置。
2. 正在有进展时，继续有界等待，并做独立的规范核对、下一批准备或已完成提交审查。
3. 执行任务请求评审时，总控独立检查 diff、必要的调用链、协议/安全边界、测试日志和对应包/提交。针对疑点复测，不重复全量跑已经可信通过的同一组检查来拖延交付。
4. 存在缺陷时发送带具体文件、证据、复现条件和验收要求的修复 TODO。执行任务的“完成”声明不自动成为总控验收结论。
5. 验收通过后，让执行任务更新 TODO、PROGRESS 和对应 evidence，并按下一节完成阶段 GitHub 同步。
6. 核实远端提交/CI后，自动分派下一批。不要问“是否继续下一阶段”。

每次 `wait_threads` 使用目标 `hostId` 和最新 cursor；有界等待建议不超过 60 秒，避免忙轮询和重复输出。工具超时不等于执行任务失败，编译慢也不能直接判定卡住。

我同时授权创建一个附着在总控任务的 heartbeat，建议每 5 分钟检查一次，用于总控空闲或中断后的继续监督。先查找并复用已有本轮 heartbeat，避免重复；通过 `automation_update` 设置，不手写伪自动化指令，不用独立 cron 替代任务 heartbeat。

heartbeat 应遵守：

- 先读取本地监督状态与目标状态，再读取执行任务增量状态。
- 已有活跃分派不重复发送，使用阶段/批次和消息记录去重。
- 状态不变或没有可执行新动作时保持安静；仅在阶段完成、失败需要处理、执行停滞且有证据、外部依赖或需要我动作时通知。
- 执行任务完成一批后唤醒总控评审；总控根据审查结果继续派发。
- 我明确停止/暂停目标时停止派发并暂停 heartbeat；不得以自动监督重新启动我叫停的工作。
- 完成整轮后关闭或暂停本轮 heartbeat，不持续空转。

保存可恢复的本地监督记录，包含目标、执行任务标识、worktree、当前批次、wait cursor、最后实质进展、待审提交、远程 jobPath、GitHub 同步状态和已发送消息标记。不保存秘密，也不把本机监督状态误提交到公开仓库。

若自动化工具不可用，维持当前 Goal 内的有界监督并说明限制，不能声称已建立跨空闲时段的自动监控。执行任务失败或退出后先检查现有进程、工作树和日志，再恢复原任务，避免遗失进度或重复创建。

## 八、每完成一个较大部分就同步 GitHub

我明确授权本轮在完成每个主要阶段，或阶段内一个较大的可独立验收闭环后，进行 GitHub 源码、文档和验收记录同步，不必等全部功能完成，也不必每次再请求推送许可。

默认同步到本轮 `codex/` 工作分支，创建或更新一个清楚的 PR。每次流程：

1. 核实 diff 和基线，只包含本轮文件，避免 `git add .` 携带无关用户文件。
2. 执行该阶段必要检查并修复失败；保留失败的根因记录，不删测试或伪造结果。
3. 更新 TODO、PROGRESS、相关协议/架构文档及真实证据，说明已通过和未运行的边界。
4. 创建聚焦的 commit，push 正确的 `Wen5555/LinkSend` 工作分支。
5. 核对远端提交确实存在，跟踪对应 CI；失败自动修复并再次同步。CI 未完成/失败时明确标识，不能把 push 成功写成验收通过。
6. 向我简报：本阶段完成内容、commit/PR 链接、关键测试结果、仍有的限制以及已经启动的下一阶段。

若需要香港服务支持新阶段，部署来自已核实阶段提交的构建，并按事务方式验证服务健康、版本、协议和 `relay=false`。有失败即修复或回滚，不把未核实 dirty 构建称作阶段部署。

阶段同步的默认交付物为工作分支、PR、构建产物与证据。合并 main、对外正式 Release 或收费签名服务仅在会话中已有明确授权时执行；否则把准确候选包和可审阅结果准备好，不将 GitHub 同步授权扩展成这些动作。不可 force-push 覆盖用户提交，不删除远端历史。

- 原生共享必须真实进入系统菜单，检查冷启动、后台、连续共享、临时文件权限和扩展关闭；快捷面板仅用真实设备状态。
- 剪贴板验证双向、多设备回环、快速复制、并发复制、离线重连、锁屏、撤销和大文件传输共存；不留持久明文内容日志。
- 对最终准确候选包记录源码提交、包哈希、系统/架构、网络环境、步骤与结果。旧构建的成功不能直接套到新包。
- 已通过的检查只在相关代码变化、失败或新疑点时扩展/重复；不为低风险文案/CSS 修改制造机械测试。

## 十、完成、阻塞与沟通

执行任务每批返回固定摘要：TODO ID 与结果、改动文件、提交/分支、实际命令与退出结果、证据路径、平台/包哈希、发现的问题、需要总控判断的事项。不要只回复“已完成”“测试都过了”。

总控验收全部 U1–U7、必要支撑工作、准确包的关键实机验证，以及已授权 GitHub/部署交付后，才可把 Goal 标记 complete。不能因为 TODO 文案全部打勾、上下文不足、时间长或预算接近上限就提前完成。

缺少签名、系统授权、主机条件等时，先完成所有不依赖它的任务，保留明确未完成项和可审阅结果。同一真实外部阻塞连续出现达到 Goal 工具规定的至少三轮、且没有独立进展可做时，才按规则标记 blocked；一次网络失败、执行任务仍在运行或尚未研究清楚都不是 blocked。

需要我输入时，一次说清：已经完成什么、准确缺什么、为什么现有授权/工具不能解决、我需做的最小一步。若暂停来自 SKILL/AGENTS 的明确要求，给出文件与原文；若来自自动审批拒绝，说明被拒绝的动作和理由。不要把自己的保守推断说成硬性规定。

工作中用简洁中文报告有意义的进展。无人需要处理且状态未变化的 heartbeat 保持安静。最终报告逐项列出七项成果、真实验证范围、GitHub 链接、安装包与来源、部署/回滚记录和明确限制。

现在开始执行：读取材料和当前状态，建立或复用 Goal，核实主机与执行任务配置，生成可验收 TODO，创建或恢复 GPT-6 medium 执行任务，启用自动监督，并派发 E0。随后持续执行上述闭环。
